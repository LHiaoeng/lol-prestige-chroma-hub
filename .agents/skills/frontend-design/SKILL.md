# Frontend Design

为原画图鉴建立鲜明、可用的视觉表达。用户只需描述期待的感受；Agent 负责构图、排版、空间和动效判断，并推荐具体方案。

全站风格统一是首要设计原则，优先于单页的新颖和表现力。遵循 `docs/design-system.md` 的一致性契约，在同一视觉语言内创新。

## 1. 默认快速路径

- 用户给出页面与目标后，自行判断构图和排版；在当前约束下选择最合适的一个方案，用一句话说明关键调整及理由，直接实施并自查，不等待审美参数或例行确认。
- 决策顺序：满足任务及功能/无障碍契约 → 全站风格一致 → 关键信息易找易懂 → 视觉表现力 → 实现与维护成本。以这套标准取舍，不声称存在客观唯一的最佳设计。
- **局部调整**：走“定位 → 复用并修改 → 针对性自查”，跳过美术方向探索。只修改解决问题所需的范围。
- **设计升级或新页面**：执行第 3 节，以一个推荐方向完成实现与全端自查，效果由用户人工确认。用户说“更高级”“更有设计感”即适用。
- **方案或评审**：只交付判断与推荐，不修改页面。只有用户要求比较时才制作多方案；仅对会实质改变结果、且无法从项目推断的信息提问。

## 信息判断先于布局

所有页面调整先在内部判断以下问题，只对用户说明最终选择与关键理由，无需另写分析文档：

- 用户到这页主要要完成什么？完成任务前必须知道哪些信息？结合实际内容、已有功能与请求推断，不把当前显示顺序当作重要性顺序，也不虚构用户调研结论。
- 按任务将内容分为核心信息、决策辅助和低频补充。核心信息直接可见且优先排列；会影响理解、选择的条件和状态靠近对应内容；补充信息可后置或渐进展开。视觉权重与任务重要性对应。
- 根据关系选择展示：同类对象用可比较的列表或网格，单项属性用资料列表，跨对象多维比较用表格，过程用有序步骤，长解释用正文。优先采用本站已有的对应组件；仅在确有表达缺口时新增可复用模式。
- 按内容选择密度：查找与比较强调可扫描和字段对齐，欣赏原画强调作品尺度，阅读强调行长与段落节奏。用真实长标题、字段数量和图片比例检验选择，避免套用固定版式。
- 保持全站同类信息的标签、视觉角色与交互一致；手机端可重排或折叠低频内容，但核心信息、关键条件和主要操作仍需容易发现。原画颜色不能随意改变全站控件配色。

自查时用一个具体任务走查：用户能否从首要内容理解本页、找到所需信息并完成操作；若需要反复展开或跨区寻找关键条件，先调整信息组织，再精修样式。

## 2. 最小上下文

以下路径均相对仓库根目录；本轮已读内容不重复加载。

1. 读取 `docs/design-system.md`，确定品牌约束；已有本轮上下文直接复用。
2. 定位目标路由、直接相关组件与 `src/styles/global.css` 的相关规则；核实实际渲染来源。先过一遍 `src/components/` 与 `src/layouts/` 清单，判断哪些能直接复用。
   选择一个成熟的同类页面作基准；新增页面类型时参考全站布局与相邻页面，明确需要继承的公共模式。
3. 仅在涉及页面契约或存在疑问时查询 `docs/frontend-design.md` 对应段落：首页第 7 节、详情第 8 节、博客第 6.1 节；路由、图片、SEO 或交互变化再查对应章节。
4. 现有文档描述的是维护契约，可能有历史残留；与实际代码冲突时核实实际消费者，记录相关差异，不照搬过时行为。

遵循用户要求和仓库约束。已验证的功能、数据、路由与 SEO 契约是边界；设计升级可以调整当前版式、字号比例和空间节奏。沿用品牌与组件能力，不把所有现有 CSS 都当作必须保持的设计。

## 3. 主动确定美术方向

设计升级时，先用一小段说明页面服务谁、主要任务、如何延续全站风格及一个记忆点，然后开始实现。单页请求默认在现有设计系统内改进；全站视觉语言变更只在对应授权范围内统一实施，范围不足时先提出迁移方案。

- 从真实原画的主体、明暗、色彩与留白提出构图；默认方向是精品数字原画展馆，具体表达随作品和页面任务变化。
- 首页建立身份与精选作品的焦点；目录服务比较和连续浏览；详情突出完整作品与资料；博客强调阅读节奏。按页面用途选择密度。
- 明确第一视觉焦点、第二层信息及主要操作。用字号比例、对齐、空间和图片尺度建立层级；装饰须服务这个层级。
- 选择一个来自本站内容的记忆点，例如作品局部与完整原画的呼应、精选作品与收藏信息的编排；不要给每个区块都加视觉噱头。
- 做一次“换主题检查”：若替换名称与图片后就能成为任意产品介绍页，重新检查关键构图是否体现原画浏览体验。
- 字体先用现有资源，通过字重、行长和中英文比例提升排版；只有现有字体确实无法表达目标时才考虑新字体及中文覆盖、加载成本。

## 4. 实现与精修

- 动手前先确认 `src/components/` 与 `src/layouts/` 的现成能力（`BaseLayout`、`ResponsiveHeroBackdrop`、`ChromaCard`、`ImageViewer`、`Filters`、`BackToTop` 等），优先复用，不重复实现已有组件已经做过的事；确认没有对应能力时才新增组件，并在交付里说明为什么不复用。目录卡片是有效内容单元，避免无意义的容器嵌套。
- 图标、按钮、标签、卡片、筛选、返回顶部、图片查看器、展开与折叠等已有实现直接沿用；页面内不另写一套同类控件。需要变体时先给现有组件加参数或修饰类，不新建平行组件。
- 使用现有语义变量；局部构图可使用组件内样式。新增全局变量需有复用理由，并更新视觉规范。
- 同类控件复用同一组件或公共样式；公共视觉规则在共享层维护，避免页面各自覆盖成不同外观。修改共享规则前定位其消费者。
- 优先调整视觉影响最大的部分：主次关系与构图、排版、间距、色彩层级，最后才是动效和装饰；不为微调启动整站改造。
- 原画浏览保留合适的裁切与完整预览；装饰背景与正文主图分别处理。使用真实标题、作品及空状态，不能用占位内容掩盖布局问题。
- 动效表达聚焦、反馈或空间关系；按需使用原生 CSS/浏览器能力，尊重触摸设备与减少动态效果，不默认引入动效库或客户端框架。
- 首页目录同时有静态卡片和浏览器重绘模板：改动卡片呈现时检查两处及相关客户端渲染，确保筛选后视觉一致。
- 换图与改文案同时走两条边界：图片只保存 `img.chromaart.lol` 对应的仓库相对路径，不提交远程图片副本；新增或修改的文案、ARIA、Placeholder 和 Alt 同时覆盖英文页与 `/zh-cn/` 中文路由。

## 5. 检查、修正与人工确认

渲染结果由用户人工查看；不启动浏览器做批量截图或视觉回归。Agent 负责保证代码层面的全端适配，并在交付时列出需要人工确认的页面、视口与状态。

1. 全端适配自查：桌面与手机断点、中英文页面（含 `/zh-cn/` 路由）、长标题与空状态；将目标页与基准页比较一致性契约。公共样式变化时覆盖每个受影响页面类型的代表页；仅当全局规则影响全站时扩展到首页、目录、详情和博客，不逐个遍历同模板路由。
   逐项对照 `docs/frontend-design.md` 第 17 节修改检查表，重点不漏：触控目标至少 44px、320px 无页面级横向滚动、图片三级回退、中英文 ARIA/Alt、无脚本可读的首屏与主要内容。
2. 按改动检查键盘焦点、触控区域、图片降级、减少动态效果，以及筛选、展开或预览等受影响状态；必要时补查断点两侧。
   原生 `<details>`（首页筛选、详情资料）关闭时会在浏览器布局层隐藏内容，即使内部元素的计算样式为 `block` 也不代表可见；改动折叠区时同时确认 `open` 状态、实际高度和内容确已输出。
3. 先批量修正自查发现的问题，再复查改动结果。完成后停止审美微调；若仍有明确缺陷，针对缺陷继续修复，不能用次数限制跳过问题。
4. 本 Skill 只做设计相关判断与改动：不运行测试、类型检查或构建命令，也不新增或修改测试。完成标准是目标页与全站风格一致、受影响功能可用且无已知阻塞缺陷；若改动可能触及页面契约、数据或 SEO，在交付时提醒需要补跑的验证。

交付按第 7 节的领域格式总结；建议人工查看的页面与视口参考 `docs/frontend-design.md` 第 16.3 节矩阵。不把源码检查描述为视觉验收。

## 6. 保持轻量

用 `rg` 定位并批量读取相关片段，不为局部改动扫描整站。默认不联网、不加载其他设计 Skills、不生成计划或多套样稿；用户明确要求或实际缺口需要时再扩展。不做截图与视觉回归，渲染效果交用户人工查看。自查通过后停止，不反复自查或增加装饰；新改动或用户反馈的具体缺陷才触发复查。最终回复按第 7 节的领域格式组织，每个受影响领域一条，不写套话。

稳定的新增视觉规则写回 `docs/design-system.md`；页面行为变化更新 `docs/frontend-design.md` 对应段落。省 Token 依靠减少重复上下文与无关流程，不省略本节的自查。

## 7. 交付总结与对齐

改动完成后，回复里按领域给出可对齐的总结，让后续修改能直接定位、复用或回滚。

- **领域与位置**：用项目既有领域名称和文件路径，不写“页面样式”这类泛称。例如 `首页 Hero`（`src/pages/index.astro`）、`ChromaCard`（`src/components/ChromaCard.astro`）、`共享视觉变量`（`src/styles/global.css`）。落在共享层或公共组件时点明影响到的页面类型。
- **改了什么**：按领域逐条说明结果，视觉变化写清具体维度（主次层级、排版与字号比例、间距节奏、图片裁切与尺度、内容密度），不用“优化了一下”这类空话。
- **怎么改的**：给出关键实现手段——复用了哪个组件或语义变量、新增规则落在哪一层（组件内样式还是共享层）、是否新增全局变量、静态与浏览器双实现是否同步。
- 一并说明已自查范围、需要人工确认的页面与视口，以及没能覆盖的部分；改动可能触及页面契约、数据或 SEO 时，提醒需要补跑的验证。

领域名称沿用 `CONTEXT.md` 与 `docs/` 的既有术语，不自造词；术语缺口交给 `/domain-modeling`。
