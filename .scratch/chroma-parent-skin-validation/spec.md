# 臻彩详情页与 CommunityDragon 数据对应规格

## Problem Statement

臻彩详情页由 `data/prestige-chromas.json` 的静态臻彩条目生成，并在浏览器中可选加载 CommunityDragon（CD）运行时资料。两套数据表达的是不同层级：静态目录负责臻彩原画、目录名称、分类和编辑型关系；CD 负责当前数据通道与本地化视图下的英雄、皮肤和炫彩资料。

本次实现不在臻彩详情页展示“皮肤补充资料 / Additional skin reference”区块，也不在该页发起 CD 补充资料请求。CD 对应关系用于生成稳定的站内运行时详情链接；目标页面自身负责加载和展示 CD 资料。

当前运行时关系没有完整闭合：页面把 `heroId` 和 `sourceSkinId` 传给 CD，先在对应英雄的 `skins` 集合中找到所属皮肤，但随后错误要求该皮肤满足 `isBase: true`。`isBase` 只表示英雄默认外观，不表示炫彩所属皮肤；普通皮肤作为所属皮肤时会被错误拒绝。

页面还没有把静态目录中的 `skinId` 与匹配到的 CD 皮肤的嵌套 `chromas[].id` 建立并校验关系。因此，只要 `sourceSkinId` 存在，当前流程就可能把一个没有对应 CD 炫彩的皮肤资料显示在臻彩详情页上。页面和 CD 数据之间应形成以下稳定 ID 关系：

```text
静态臻彩条目
  heroId
    -> CD Champion.id
      sourceSkinId
        -> Champion.skins[].id（炫彩所属皮肤）
          skinId
            -> 匹配所属皮肤的 chromas[].id（当前炫彩）
```

当前页面还使用“原皮 / Base skin”和 `baseSkin` 作为所属皮肤的称呼，这会把“炫彩所属皮肤”和“英雄默认外观”混为一谈，与项目领域词汇冲突。

详情页中的关联资料还需要具备明确的站内导航。英雄、所属皮肤、皮肤系列、皮肤宇宙和其他臻彩都应点击进入各自已有的详情页或臻彩页；不能只显示为不可点击文字，也不能用搜索引擎外链替代已有的站内运行时资料页。

## Solution

让臻彩详情页把 CD 资料视为同一条 ID 关系链上的站内导航目标，而不是用名称或 `isBase` 推断关系。

核心对应关系如下：

| 静态臻彩字段 | CD 关系 | 语义 |
| --- | --- | --- |
| `heroId` | `Champion.id` | 英雄边界；必须先限定到同一个英雄记录 |
| `sourceSkinId` | `Champion.skins[].id` | 炫彩所属皮肤的稳定 ID |
| `skinId` | 匹配皮肤的 `chromas[].id` | 当前静态臻彩对应的 CD 炫彩 ID |
| `heroNameZh` / `heroNameEn` | `Champion.name` | 同一英雄的展示名称；名称不参与身份匹配 |
| `skinNameZh` / `skinNameEn` | 匹配皮肤的 `Skin.name` | 同一所属皮肤的展示名称；名称不参与身份匹配 |
| `skinSets[].id` | 匹配皮肤的 `skinlineIds[]` | 可核对的皮肤系列关系；静态名称仍由目录提供 |
| `universes[].id` | 匹配皮肤的 `universeIds[]` | 可核对的皮肤宇宙关系；静态名称仍由目录提供 |

静态臻彩名称、臻彩原画、颜色、描述、分类、分类图标、版本、排序和相关臻彩分组没有一一对应的 CD 字段，继续由静态目录负责。CD 的名称、描述和媒体只作为运行时所属皮肤/炫彩资料补充，不能替换静态臻彩正文。

当三段 ID 关系都成立时，英雄、所属皮肤和其他 CD 运行时详情链接应指向同一个英雄边界及其所属皮肤。`isBase` 可以继续作为 CD 皮肤属性展示或投影所需的元数据，但不得参与所属关系合法性判断。

当英雄、所属皮肤或对应炫彩任一关系不存在时，目标运行时详情页显示现有明确的 `not-found` 失败状态；臻彩静态详情页仍保留站内链接，不得回退到默认外观、第一项、同名对象或其他英雄的记录。

详情页导航对应关系如下：

| 页面内容 | 目标页面 | 目标参数 |
| --- | --- | --- |
| 英雄 | 英雄详情壳 | `id=heroId` |
| 炫彩所属皮肤 | 皮肤详情壳 | `id=sourceSkinId`、`champion=heroId` |
| 每个皮肤系列 | 皮肤系列详情壳 | `id=skinSets[].id` |
| 每个皮肤宇宙 | 皮肤宇宙详情壳 | `id=universes[].id` |
| 相关臻彩卡片 | 臻彩静态详情页 | 对应臻彩的 `slug` |

以上站内目标都必须使用当前页面语言的本地化路径。英雄、所属皮肤、皮肤系列和皮肤宇宙属于 CD 运行时页面，当前详情页选择 `latest` 时必须把 `channel=latest` 传递到目标；默认 `pbe` 可以沿用项目默认值。外部搜索、SkinSpotlights、模型站和版本公告仍保留为明确的外部操作，不得与站内导航混为一谈。

## User Stories

1. 作为访客，当臻彩属于英雄默认外观时，我可以看到对应的 CD 所属皮肤资料和炫彩关系。
2. 作为访客，当臻彩属于 `isBase: false` 的普通皮肤时，我仍可以正常看到对应的 CD 所属皮肤资料。
3. 作为访客，我看到的 CD 所属皮肤一定来自 `heroId` 对应的同一个英雄。
4. 作为访客，我看到的 CD 所属皮肤一定是 ID 等于 `sourceSkinId` 的皮肤。
5. 作为访客，我看到的 CD 炫彩一定是该所属皮肤 `chromas[]` 中 ID 等于 `skinId` 的炫彩。
6. 作为访客，即使其他英雄或其他皮肤存在同名对象，系统也不会错误关联它们。
7. 作为访客，当 `sourceSkinId` 不存在于当前英雄的皮肤集合时，我会看到现有明确的所属皮肤未找到状态。
8. 作为访客，当 `skinId` 不存在于匹配所属皮肤的 `chromas[]` 时，我会看到明确的炫彩未找到状态。
9. 作为访客，当网络、HTTP、解析或数据契约失败时，静态臻彩正文仍然可读，并继续使用现有错误与重试反馈。
10. 作为访客，PBE 与正式服数据通道会对英雄、所属皮肤和炫彩使用同一个选定通道。
11. 作为访客，英文页面只使用 `default` 本地化视图，中文页面只使用 `zh_cn` 本地化视图，不跨视图拼接 CD 事实。
12. 作为访客，页面中的英雄入口使用 `heroId`，所属皮肤入口使用 `sourceSkinId`，臻彩模型入口使用 `sourceSkinId` 与 `skinId` 的组合。
13. 作为维护者，我可以清楚区分“炫彩所属皮肤”和“英雄默认外观”。
14. 作为维护者，我不会看到代码使用名称、slug、数组位置或 `isBase` 建立炫彩所属关系。
15. 作为维护者，我可以从运行时补充数据中同时得到匹配的 `sourceSkin` 和 `chroma`。
16. 作为维护者，我有自动化测试防止非默认所属皮肤再次被拒绝。
17. 作为现有用户，首页、博客、静态臻彩标题、原画、分类和描述不会因为接入 CD 关系校验而改变。
18. 作为现有用户，取消请求、重试、频道切换、本地化页面和失败降级行为保持不变。
19. 作为访客，我可以从臻彩详情页点击英雄名称进入对应英雄详情页。
20. 作为访客，我可以从臻彩详情页点击所属皮肤名称进入对应皮肤详情页。
21. 作为访客，我可以点击每个皮肤系列名称进入对应的皮肤系列详情页。
22. 作为访客，我可以点击每个皮肤宇宙名称进入对应的皮肤宇宙详情页。
23. 作为访客，我可以点击相关臻彩卡片进入对应的臻彩详情页，而不会被带到同名或错误 ID 的内容。
24. 作为访客，在中文页面点击关联内容时，我仍然停留在中文路径；在英文页面点击时，我仍然停留在英文路径。
25. 作为访客，当 CD 资料加载失败时，已生成的站内链接仍然可以导航到对应的运行时页面并显示其自身的失败状态。
26. 作为维护者，我可以通过构建产物检查臻彩详情页没有指向不存在的站内关联路径。

## Implementation Decisions

1. 保持静态目录作为臻彩详情页的主要内容来源；本规格只扩展运行时 CD 资料的身份对应，不迁移静态 JSON 契约。
2. 运行时请求使用静态条目的 `heroId` 读取对应 CD 英雄记录，并在该记录内部完成所属皮肤和炫彩匹配。
3. 运行时输入同时携带英雄 ID、所属皮肤 ID 和炫彩 ID；炫彩 ID 由静态 `skinId` 传入运行时关系边界，但内部可使用语义明确的 `chromaId` 命名。
4. 所属皮肤只允许通过当前英雄的 `skins[].id === sourceSkinId` 精确匹配；不得跨英雄搜索、按名称搜索、按数组位置选择或回退到 `isBase: true` 的皮肤。
5. 当前所属皮肤找到后，只允许通过该皮肤的 `chromas[].id === skinId` 精确匹配当前炫彩；不得在其他皮肤的炫彩集合中搜索或只因为所属皮肤存在就视为匹配成功。
6. CD 英雄资源已经包含皮肤及其嵌套炫彩关系；实现应在现有英雄资源和运行时缓存边界内完成匹配，不引入新的 `skins.json` 请求。
7. 运行时补充数据模型使用 `sourceSkin` 表示炫彩所属皮肤，使用 `chroma` 表示匹配到的 CD 炫彩；不得继续使用 `baseSkin` 表示所属皮肤。
8. 删除 `isBase: true` 作为所属皮肤合法条件的校验；`isBase` 的含义仍保持为“是否为英雄默认外观”。
9. 所属皮肤或炫彩缺失时保留可识别的 `not-found` 错误映射；不得以空对象、默认皮肤或静态名称掩盖非法关系。
10. 页面仍保留现有静态 DOM 和视觉结构，但所属皮肤相关的界面文案应使用“所属皮肤 / Chroma parent skin”语义，不得使用“原皮 / Base skin”指代任意炫彩所属皮肤。
11. 运行时所属皮肤链接继续使用英雄 ID 与所属皮肤 ID；臻彩外部模型链接继续使用所属皮肤 ID 与静态炫彩 ID 的组合，不能把两个 ID 互换。
12. 静态 `skinSets` 和 `universes` 的名称继续由目录提供；若实现核对 CD 关系，只能按 ID 核对，不得用名称替代 ID，也不得因可选关系字段暂时缺失而改变静态正文。
13. 保持现有数据通道、本地化视图、请求取消、请求缓存、重试、失败保留和 URL 状态行为不变。
14. 不新增 CD 独立炫彩详情页；CD 中的炫彩仍视为所属皮肤下的嵌套资料，臻彩详情页继续是本站静态臻彩原画页面。
15. 英雄名称必须导航到英雄详情壳；所属皮肤名称必须导航到带有英雄边界的皮肤详情壳；每个皮肤系列和皮肤宇宙名称必须分别导航到现有的系列和宇宙详情壳。
16. 所属皮肤的站内链接应在静态详情页首次渲染时就能由 `heroId` 与 `sourceSkinId` 生成，不得等待 CD 请求成功；CD 成功后验证得到的 `sourceSkin.id` 必须生成同一个目标。
17. 相关臻彩继续使用对应静态条目的 slug 进入臻彩详情页，并保留当前语言；相关卡片不能只展示图片或文字而没有可访问链接。
18. 站内运行时链接必须使用稳定 ID，不得使用名称、slug 或 CD 返回的展示文本拼接目标地址；外部操作链接继续使用现有新窗口和安全属性。
19. 臻彩详情页不渲染独立的 CD 补充资料区块，不在该页发起 CD 数据请求；CD 数据请求由目标运行时详情页负责。

## Testing Decisions

1. 最高价值测试 seam 是现有臻彩运行时补充加载器；使用模拟 CD 英雄响应覆盖完整的三段 ID 关系，不重新搭建请求层。
2. 新增核心回归用例：当前英雄包含一个 `isBase: false` 的所属皮肤，该皮肤的 `chromas[]` 包含目标 `skinId`；加载成功，并将该皮肤作为 `sourceSkin`、该嵌套记录作为 `chroma` 交给视图。
3. 保留 `isBase: true` 所属皮肤成功用例，证明默认外观仍然可以是所属皮肤，但不再是必要条件。
4. 覆盖所属皮肤缺失、炫彩缺失、炫彩只存在于同一英雄的其他皮肤以及目标关系跨英雄的失败场景；每种场景都必须保持明确的 `not-found` 结果。
5. 测试应断言匹配结果的 ID 和对象身份，而不只断言最终返回 `true`，以确保没有通过名称或错误对象获得假阳性。
6. 更新运行时补充模型与 DOM 视图测试，断言使用 `sourceSkin` 和 `chroma`，并断言输出的所属皮肤链接使用 `sourceSkin.id`。
7. 保留或补充频道、本地化视图、网络失败、解析失败、重试、取消和旧内容保留测试，证明关系修复不改变既有运行时控制流。
8. 增加页面结构回归测试，确认静态臻彩标题、原画、分类、颜色、描述、版本和相关分组没有被 CD 运行时数据替换。
9. 实施完成后运行相关 Vitest、类型检查与发布构建；本次不修改目录数据，不需要数据迁移。
10. 页面构建测试应读取至少一条英文和中文臻彩详情产物，断言英雄、所属皮肤、皮肤系列、皮肤宇宙和相关臻彩使用正确的站内路径与 ID/slug。
11. 页面导航测试应覆盖带 `channel=latest` 的详情页，确认英雄、所属皮肤、系列和宇宙链接不会丢失当前数据通道；默认 PBE 链接遵守现有默认值约定。
12. 运行时 DOM 测试应断言成功加载后的英雄链接和所属皮肤链接分别使用 `champion.id` 与 `sourceSkin.id`，并使用正确的当前语言路径。
13. 站内链接回归测试应覆盖不存在的可选 CD 数据：目标页面仍生成，目标页面自己的运行时失败状态不应导致臻彩详情页丢失链接。
14. 页面结构回归测试应确认臻彩详情页不包含“皮肤补充资料 / Additional skin reference”区块或其加载脚本。

## Out of Scope

- 不把 `data/prestige-chromas.json` 改造成 CD 快照，也不修改其现有字段契约。
- 不用 CD 名称、描述或媒体替换静态臻彩标题、臻彩原画、分类、颜色、描述和版本信息。
- 不修改 `isBase` 的 CD 数据含义、Schema 或其他皮肤目录投影规则。
- 不生成独立的 CD 炫彩实体页面、炫彩 SEO 页面或新的静态臻彩页面。
- 不请求完整 `skins.json` 来完成臻彩详情的基本对应关系。
- 不要求运行时对所有静态皮肤系列、宇宙描述或分类字段做实时一致性校验。
- 不为缺失的英雄、所属皮肤或炫彩增加宽松回退或跨英雄匹配。
- 不改变首页、博客、PBE 新增页及其他运行时资料页的页面规划。
- 不新增新的站内详情路由；导航只复用现有的英雄、皮肤、皮肤系列、皮肤宇宙和臻彩详情页面。
- 不把站内关联导航改成搜索引擎、SkinSpotlights、模型站或其他外部链接；这些仍属于独立的外部操作。
- 不修改第三方网站入口、外部模型链接协议或部署流程。

## Further Notes

- CD 没有独立于所属皮肤的炫彩详情实体页面；炫彩是所属皮肤记录中的嵌套资料。因此臻彩详情页与 CD 的正确对应目标是“英雄 → 所属皮肤 → 嵌套炫彩”，而不是把臻彩当成独立 CD 皮肤。
- `sourceSkinId` 是炫彩所属皮肤 ID，不能因为英文界面历史上显示 `Base skin` 就解释为英雄默认外观 ID。
- 静态目录中的 `skinId` 是管理系统保留的字段名，但在与 CD 建立关系时表达目标 `RuntimeChroma.id`；运行时内部命名应优先使用 `chromaId` 或 `chroma` 以消除歧义。
- `heroName`、`skinName`、CD 名称和 slug 都是展示信息；跨通道、跨本地化视图和跨页面的身份判断一律以稳定数字 ID 为准。
- 原有“只修复 `isBase` 校验”的范围已扩展为完整关系校验：必须同时保证 `heroId`、`sourceSkinId` 和 `skinId` 三段关系对应，才能宣称臻彩详情与 CD 资料一致。
