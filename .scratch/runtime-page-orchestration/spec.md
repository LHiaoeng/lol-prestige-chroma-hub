# 运行时资料页面编排规格

## Problem Statement

LoL Chroma Art 的运行时资料页面已经能够加载英雄、皮肤、皮肤系列、皮肤宇宙和 PBE 新增资料。外层的 `pbe` / `latest` 通道切换、取消、旧结果保护、历史导航和成功后提交 URL 已由共享的运行时通道生命周期 module 负责。

但进入一个运行时页面后，页面内部的资料编排仍然分散在多个异步路径：核心资料、英雄列表的宇宙所属系列、皮肤的系列/宇宙关系、皮肤系列的完整皮肤集合、皮肤宇宙的分组皮肤集合分别加载，并分别拥有成功、失败、重试和空状态处理。`RuntimeController` 需要协调这些路径，`RuntimeView` 又通过多个可选的渲染和失败方法接收它们。

对访客而言，核心资料和补充资料应该有清晰且稳定的关系：核心资料成功后立即可读，补充资料可以继续加载；某一个补充资料失败时不应清空核心资料或其他已经成功的关系；重试某个补充资料时不应重新加载整个页面；用户切换实体或数据通道时，旧页面的补充结果不应写入新页面。

当前页面状态主要隐藏在 DOM view 的 slot、闭包变量和多个回调之间。维护者需要同时理解控制器的请求顺序、generation 判断、可选 view 方法和 DOM slot 状态，才能判断一个局部失败是否会影响核心内容。测试也必须构造一组包含许多可选方法的 view stub，才能验证页面的局部失败行为。

## Solution

建立一个运行时资料页面编排 module，负责把一次页面加载拆成“核心资料”和若干独立的补充资料 slot，并为每个 slot 管理 `loading`、`ready`、`empty`、`failed` 状态和只重试当前 slot 的行为。

该 module 复用已经完成的运行时通道生命周期 module，不重新实现 channel、History API、取消和旧结果保护。外层生命周期确定当前有效的页面状态后，页面编排 module 负责加载核心资料、根据核心资料规划允许的补充资料、提交核心状态、独立提交补充状态，并在页面状态失效时停止所有补充结果。

DOM view 改为消费页面编排 module 提供的稳定页面状态或状态事件，不再直接对应多个异步请求方法。页面展示仍保留核心资料优先、关联资料渐进加载、局部失败和独立重试的现有用户体验；本规格不改变资料内容、路由、SEO 或 CommunityDragon 的读取规则。

## User Stories

1. 作为访客，我希望进入英雄列表时先看到英雄核心列表，以便不必等待额外的宇宙关系名称才能开始浏览。
2. 作为访客，我希望英雄列表的搜索、职业筛选、排序和分页在核心列表成功后即可使用，以便补充关系资料不会阻塞目录操作。
3. 作为访客，我希望宇宙列表的核心卡片先出现，以便所属皮肤系列名称加载较慢时仍能浏览宇宙。
4. 作为访客，我希望宇宙列表的所属系列名称独立显示加载、成功、缺失和失败状态，以便我知道卡片缺少的是关系资料而不是宇宙本身。
5. 作为访客，我希望皮肤详情先显示英雄、皮肤名称、稀有度、媒体、阶段和炫彩等核心资料，以便关联资料失败不会阻断主要内容。
6. 作为访客，我希望皮肤详情的皮肤系列和皮肤宇宙关系在核心资料之后独立加载，以便核心内容可以先阅读。
7. 作为访客，我希望皮肤详情的系列关系加载失败时仍可查看核心皮肤资料，以便单个关系目录故障不会让详情页失效。
8. 作为访客，我希望皮肤详情的宇宙关系加载失败时仍可查看核心皮肤资料和已经成功的系列关系，以便局部失败不会扩大影响。
9. 作为访客，我希望皮肤系列详情先显示系列名称、描述和宇宙关系，以便完整皮肤集合较大或失败时仍能理解系列资料。
10. 作为访客，我希望皮肤系列的完整皮肤集合独立显示加载、空集合、失败和重试状态，以便集合请求不会覆盖系列核心资料。
11. 作为访客，我希望重试皮肤系列的完整皮肤集合时只重新请求该集合，以便不必重新加载系列核心资料和宇宙关系。
12. 作为访客，我希望皮肤宇宙详情先显示宇宙名称、描述和皮肤系列关系，以便分组皮肤集合较慢时仍可浏览宇宙资料。
13. 作为访客，我希望皮肤宇宙的分组皮肤集合按皮肤系列分别显示，以便能够区分不同关系组的内容。
14. 作为访客，我希望皮肤宇宙的分组皮肤集合失败时核心宇宙资料和系列导航仍保留，以便只重试受影响的集合。
15. 作为访客，我希望某个补充资料返回空集合时看到明确的空状态，而不是无限加载或被误判为请求失败。
16. 作为访客，我希望核心资料请求失败时看到完整的页面失败和重试状态，以便知道当前页面的主要资料没有加载成功。
17. 作为访客，我希望补充资料请求失败时看到与核心资料失败不同的局部错误提示，以便知道页面仍有可用内容。
18. 作为访客，我希望补充资料重试成功后错误提示只在对应区域消失，以便其他区域的状态不被意外重置。
19. 作为访客，我希望切换到另一个实体后旧实体的关系、皮肤集合和失败按钮不再出现在新实体页面，以便页面状态不会串页。
20. 作为访客，我希望切换数据通道后新通道的核心资料与所有补充资料重新建立对应关系，以便不会把旧通道的关联内容混入新通道。
21. 作为访客，我希望快速离开页面或切换通道时，已经取消的补充请求不会在稍后修改页面，以便页面始终显示当前选择。
22. 作为访客，我希望同一个补充资料失败后重复点击重试不会并行产生多个重复请求，以便页面状态和网络请求保持可预测。
23. 作为键盘和屏幕阅读器用户，我希望核心资料、补充资料、空状态、失败和重试状态都能被感知，以便不依赖视觉布局理解页面进度。
24. 作为维护者，我希望核心资料与补充资料的状态模型集中在一个页面编排 module 中，以便局部失败规则不会散落在多个控制器方法和 DOM slot 中。
25. 作为维护者，我希望页面 view 只消费页面状态，不必知道每一种补充资料请求的重试闭包，以便 view 的 interface 更小、更稳定。
26. 作为维护者，我希望不同页面模式复用同一套补充资料状态语义，以便英雄列表、皮肤详情、皮肤系列详情和皮肤宇宙详情不会各自发明失败表示。
27. 作为维护者，我希望补充资料的请求策略仍由 CommunityDragon 运行时资料 module 提供，以便页面编排不复制 URL、Schema、缓存或错误分类规则。
28. 作为测试维护者，我希望通过一个页面编排 seam 控制核心和补充请求的完成顺序，以便稳定覆盖局部失败和旧结果场景。
29. 作为测试维护者，我希望只验证页面状态和用户可见行为，而不是验证具体的 Promise 组织方式，以便未来调整内部实现不会造成无意义的测试重写。
30. 作为站点维护者，我希望 PBE 新增比较继续保持必要资料全部成功后才展示完整差集，以便页面编排不会把原本的原子比较误改成部分结果。

## Implementation Decisions

- 建立一个运行时资料页面编排 module，作为核心资料与补充资料之间的唯一主要 seam；它复用已完成的运行时通道生命周期 module。
- 页面编排 module 的职责是规划页面资料、启动核心加载、根据核心结果启动允许的补充加载、维护每个补充 slot 的外部状态，以及为每个 slot 提供独立重试。
- 核心资料是页面提交的前置条件。核心请求失败时，页面进入核心失败状态；核心请求成功后，页面可以提交核心内容并启动补充资料。
- 补充资料不阻塞核心资料。补充资料的加载、成功、空集合和失败状态必须独立于核心资料状态表达。
- 每个补充 slot 至少区分 `loading`、`ready`、`empty` 和 `failed`；slot 失败必须保留已经成功的核心资料和其他 slot 内容。
- 补充 slot 的重试只重新执行该 slot 的加载操作。重试不重新请求核心资料，不重建无关 slot，不改变已经成功提交的核心 URL。
- 补充 slot 需要携带当前页面状态和当前通道上下文；页面状态或通道失效后，旧 slot 结果不得提交。
- 页面编排 module 使用外层运行时通道生命周期提供的当前请求上下文和 `isCurrent` 语义，不自行创建第二套 channel generation 或 History API 提交规则。
- 页面实体变化时，所有旧补充 slot 都必须被清理或标记失效；新实体只能显示新核心资料及其新规划的 slot。
- 皮肤详情的系列关系和宇宙关系可以并行加载，但各自失败和重试必须独立；一个关系请求失败不能阻止另一个关系请求成功。
- 皮肤系列详情的完整皮肤集合继续按需读取；其失败只影响集合 slot，不影响系列核心资料和宇宙关系。
- 皮肤宇宙详情的完整皮肤集合继续按需读取，并按已知皮肤系列关系形成分组；集合失败只影响集合 slot，不影响宇宙核心资料和系列导航。
- 宇宙列表的所属系列名称继续作为列表补充 slot；列表卡片核心资料成功后即可展示，关系名称单独更新。
- 运行时页面 view 的 interface 收敛到页面状态或页面状态事件，不再要求调用方逐一实现核心、关系、集合和各自失败方法。
- 页面 view 仍负责 DOM 结构、媒体展示、链接、文本本地化、无障碍属性和重试按钮；页面编排 module 不直接创建 DOM。
- `CommunityDragonRuntime` 继续负责资料读取 adapter、请求去重、缓存、Schema 校验、结构化错误和资源路径；页面编排不复制这些规则。
- `pbe-additions` 继续作为原子比较页面处理：任一必要集合失败时不提交部分差集；该页面不被改造成普通的核心/补充 slot 页面。
- 外部错误仍按现有结构化错误分类处理；取消和失效请求不展示普通失败，真实失败交给页面状态展示。
- 不改变 `pbe` / `latest` token、英文 `default` 与中文 `zh_cn` 本地化视图规则、页面 URL、详情 `noindex` 或 sitemap 规则。
- 不保留长期并行的旧多方法 view interface 和新页面状态 interface；迁移完成后删除已经不再需要的协调回调和隐藏 slot 状态。
- 不新增客户端框架、持久缓存、代理、数据库或服务端运行时依赖。

## Testing Decisions

- 测试只验证页面编排 module 的外部行为：核心优先、补充状态、局部失败、独立重试、空集合、实体切换、通道失效和取消；不绑定内部函数名称、Promise 数量或 DOM 节点组装顺序。
- 主要测试 seam 是页面编排 module，注入假的 CommunityDragon runtime 和可观察的页面状态 adapter；测试不访问真实 CommunityDragon。
- 使用可控的 deferred 请求夹具，分别控制核心请求、关系请求和完整皮肤集合请求的完成顺序，以便验证核心先提交和补充后更新。
- 测试英雄列表的宇宙系列 slot：核心列表成功后立即可用，关系成功会更新名称，关系失败显示局部错误并可单独重试。
- 测试皮肤详情的关系 slots：系列和宇宙请求可并行；任一失败不清除核心资料或另一个成功的关系；失败 slot 可独立重试。
- 测试皮肤系列详情的集合 slot：核心系列资料先显示，集合成功显示资料项，空集合显示空状态，集合失败只显示集合错误并支持单独重试。
- 测试皮肤宇宙详情的分组集合 slot：核心宇宙和系列关系先显示，集合成功按系列提交分组，集合失败不清除核心资料和系列导航。
- 测试核心请求失败：不启动依赖核心结果的补充请求，页面显示核心失败和整体重试入口。
- 测试补充请求失败：核心内容保持不变，补充 slot 进入 failed，重试只触发对应的请求。
- 测试补充请求返回空集合：状态为 empty，不显示失败文案，不产生无限 loading 状态。
- 测试实体切换和通道切换：旧核心和旧 slot 的 deferred 结果到达后都不能修改新页面；新页面的核心和补充状态只来自新上下文。
- 测试取消：取消不显示普通错误，不触发错误重试，不提交旧 slot 结果。
- 测试重复重试：同一 slot 在请求未完成时不会创建不受控制的重复并发状态；若产品需要允许并发，必须保持最后有效上下文规则不变。
- 测试 view adapter 的外部行为：各 slot 的 loading、ready、empty、failed 状态可访问，重试按钮指向正确 slot，核心内容不会因补充失败消失。
- 复用现有 `RuntimeController` 测试、运行时 DOM 测试和共享通道生命周期测试的 prior art；删除只验证旧回调调用次数的脆弱断言，保留用户可观察行为断言。
- 继续运行 `pnpm test`、`pnpm typecheck` 和构建审计；本次不降低已有的运行时错误、通道切换、取消、无障碍和浏览器导航覆盖。
- 完成自动化验证后，真实浏览器至少验收英雄列表、皮肤详情、皮肤系列详情和皮肤宇宙详情，分别观察核心先出、补充加载、局部失败、单独重试、通道切换和返回导航。

## Out of Scope

- 不重新实现或修改已完成的运行时通道生命周期 module；本规格只消费它提供的当前上下文、取消和旧结果保护。
- 不拆分或全面重写 DOM view 的媒体、卡片、分页、颜色、文案和无障碍细节；只调整其接收页面状态的 interface。
- 不改变 CommunityDragon 资源读取 adapter 的 URL、Schema、缓存、请求去重、错误分类或完整 `skins.json` 访问边界。
- 不改变运行时资料的数据模型、皮肤阶段投影、identity、去重、排序或 PBE 差集规则。
- 不新增实体页面、列表页面、路由、SEO、sitemap、静态图鉴内容或博客内容。
- 不把补充资料改成阻塞核心资料的请求，也不把所有补充资料合并成一个不可局部失败的请求。
- 不把 PBE 新增页改为允许展示部分比较结果；必要集合失败时仍保持原子失败语义。
- 不增加服务端代理、持久客户端缓存、轮询、自动刷新、客户端框架或外部错误监控。
- 不改变 `pbe` / `latest`、`default` / `zh_cn` 的技术语义或玩家界面文案。

## Further Notes

- 第一项“统一运行时通道生命周期”已实现并由 `RuntimeChannelLifecycle` 提供外层 seam；本规格依赖该结果，避免再次复制取消、generation、历史 URL 和通道提交逻辑。
- 当前页面编排的主要摩擦不是缺少一个新的数据源，而是核心资料与补充资料之间的状态没有形成单一、可观察的页面模型。
- 最终 deep module 的 interface 应让调用方只需理解页面状态和 slot 语义，而不必理解每个 CommunityDragon 请求的完成顺序。
- 如果实现过程中发现某个页面的补充资料无法遵守独立 slot 语义，应记录具体数据依赖和用户可见理由，再决定是否需要扩展本规格；不要默默把所有请求重新合并为一个大请求。
- 如果需要改变 ADR-0002 中的静态/运行时资料边界、完整皮肤集合访问边界或浏览器直接读取策略，应另行记录 ADR。
